## Product outcome and boundaries

An enabled factory takes a retained candidate from an exact human-released brief, freezes it, runs independent checks and a fresh read-only model review, repairs bounded in-scope failures through the existing Codex adapter, and delivers one draft PR. Existing watches feed actionable CI/review changes back to that same factory owner. The operator reviews and merges; the factory records the observed outcome and offers safe cleanup.

Reuse the local execution host, supervisor, managed worktrees, app SQLite, typed actions, planning conversation, prepared-diff/review surfaces, scheduler and GitHub conditional cache. Do not build a coding agent or new model/tool execution loop, revive the removed Autopilot coordinator, route Codex through Kilo, or add OpenCode/remote provisioning, auto-merge or deployment. The factory owns orchestration and evidence; Codex owns code changes. Planned check supervision requires a new typed bounded process contract. The existing local Codex host does not already support arbitrary check commands; reuse its lifecycle patterns while adding and testing this distinct capability.

The manager boundary decision deliberately uses an explicit approve-delivery touchpoint for the existing release policy: `factoryPolicy` with `publish:false` gains neither publication nor repairs on upgrade. After inspecting a retained exact-version candidate, the human grants scoped checks, at most two repairs and draft-PR publication with at most three hours cumulative execution. Only then do ordinary checks, repairs and publication proceed without another gate. Releasing a new brief alone does not imply this delivery grant. Issue comments, reviewer prose and chat cannot grant authority.

### Proposed authorization API and UI

Proposed typed action `authorize-candidate-delivery` accepts an idempotency request ID, expected execution version, candidate ID/digest, release ID, spec version/hash, target repository/base/head and current config digest. The server resolves these against authoritative local state and atomically persists an immutable **CandidateDeliveryAuthorization** with actor/time, exact candidate and release identity, target snapshot, config/policy digest, scoped check contract, `maxRepairs: 2`, `maxExecutionMs: 10800000` (or stricter configured limits), and draft-only publication. Reject stale/mismatched snapshots and replay with changed payload. A matching replay returns the same authorization, never fresh budget. No provider effect occurs inside this action.

The authorization covers the initial authorized candidate and only its bounded in-scope repair descendants; every descendant records the grant and parent revision. A manual edit, changed release/spec/target/config or unrelated candidate invalidates pending authority and requires a fresh exact human decision. Automatic repair revisions invalidate certification but do not require repeated authorization. This slice does not expose same-release budget extensions. Exhaustion returns to planning; a revised brief requires a new exact release and candidate grant. The old execution keeps its consumed history and cannot be regranted to reset its budget.

Proposed read state exposes `authorization-required`, active/revoked/stale authorization, exact candidate/spec/digest and target, allowed checks/repairs/draft publication, consumed/reserved/remaining time and repair count. The workbench must show these before the human authorizes and throughout execution, alongside revoke/cancel and the planning intervention link. Avoid a generic approve button without a visible revision and budget. Backend actions enforce the same snapshot even if the UI is stale. This is deliberate naive sequencing for the old release policy, not automatic upgrade of `publish:false`, and grants no merge authority.

## Revision, evidence and authority contracts

- **FactoryExecution:** stable execution/work/release IDs, immutable spec version/hash, repo/source/context/policy fingerprints, base SHA, version, ownership generation, active attempt/candidate, durable budget ledger and state. A unique release binding starts one aggregate; each child attempt has a unique request ID and parent/finding/event identity. Migrate the initial Slice 2 attempt without changing its historical result. Initial and repair attempts share the existing global single-writer reservation and per-repo/worktree guard; no separate repair writer pool.
- **CandidateRevision:** candidate ID, execution/attempt ID, spec and validation-contract hashes, original base/head SHAs, immutable `treeSha`, complete retained tracked/untracked manifest digest and evidence references. Slice 2 `headSha` alone cannot identify dirty/untracked content. Under a verified-dead claim, compare retained content with current content and create a Git tree using a private alternate index. Do not create a synthetic commit or mutate the original retained checkout, its real index, branch/head or receipt. Unexpected drift blocks rather than silently adopting new files. Persist the tree identity and retained digest with the freeze intent; replay recovers that immutable tree. Keep its objects reachable for the evidence retention period without manufacturing a commit.
- **ValidationContract:** exact repository-configured check commands, checkout context, bounded execution/output policy and version/hash, stored outside candidate-writable files. The released acceptance criteria guide independent code review and human acceptance; initial certification does not claim every criterion or UI behavior was exercised. Repository scripts may execute only under the approved command/policy contract; changed scripts/tests/dependencies are explicit reviewer inputs, never permission to weaken required checks. Missing commands or a usable execution environment block validation. Checks may assert required artifacts, but a separate per-scenario/browser-artifact admission harness is deferred. Show actual evidence and unproven acceptance criteria to the human before merge.
- **CheckEvidence:** candidate/contract IDs, job/receipt identity, actual argv/cwd, toolchain/environment fingerprint without secrets, start/end, exit/signal, bounded log/artifact digest, before/after tree and status. Materialize the exact certified `treeSha` in a separate managed verification checkout with private test-data/config directories and no inherited delivery credential environment, preserving the explicit original base/head-to-tree mapping. Verify the materialized tree before execution. Evidence identifies this tree and the actual checkout context; it must not claim checks ran against the later publication commit. Generated tracked/untracked changes must be reported and invalidate certification; accepted generated changes become a new candidate. A missing/uncertain receipt, cancellation, timeout or incomplete output cannot pass.
- **ReviewEvidence:** fresh read-only reviewer submission/session, configured model/prompt version, candidate/spec/contract/check-bundle hashes, structured findings with file/line and acceptance-case references, verdict `pass`, `changes-required` or `blocked`. Input includes the full diff, unexpected files, changed tests/dependencies, released acceptance criteria and executed check evidence. A code-review pass is not a separate proof of visual/behavioral acceptance. The reviewer has no edit, shell-write, repair, publish or merge tools. Invalid, incomplete or stale submissions cannot pass; findings do not execute actions.
- **Certification:** joins successful required check receipts and a passing fresh review for exactly one candidate/spec/contract/evidence bundle. A changed candidate, base, spec, required evidence or policy invalidates eligibility. Recheck at admission and immediately before delivery; retain old evidence as history, never reuse its green status for a new revision.

Suggested states: `candidate-retained → freezing → checking → reviewing → deliverable → delivering → watching → merged|closed`. Failures branch to `repair-pending`, `blocked-validation`, `needs-human`, `cancelled` or `needs-reconcile`. Repairs produce a new revision and return through checking/reviewing. Uncertain ownership never launches a replacement process. A PR receipt and a terminal execution receipt are different facts.

## Bounded repair and human planning

A **RepairRequest** binds the current candidate, exact release, failing check/review or normalized PR event, scoped instructions, attempt ordinal and remaining budget. Reserve it atomically before acquiring workspace/process resources. Reuse the local host and Codex adapter with a fresh session and a new managed workspace seeded from the authorized tree; preserve the original checkout and frozen context. New attempt/session receipts link to prior evidence. Fresh sessions avoid adding resume compatibility to this slice.

Default limits retain one active coding writer globally and at most 45 minutes per coding attempt. The manager narrows the proposal to at most two repairs total under a candidate delivery authorization, including later PR-feedback repairs, and three hours cumulative active execution per factory execution. Neither a new feedback batch nor a repair revision resets that allowance. Snapshot already-consumed initial execution when granting authorization; three hours is a cumulative ceiling, not three additional hours after coding. Persist finite check/reviewer time/output/call limits and charge verification/review as well as coding against the execution budget. Human wait is separate. Replayed events, controller restart, changed process IDs and new candidate revisions cannot reset accounting. Unknown in-flight usage reserves its maximum until reconciled; unavailable provider cost remains unknown.

Ordinary in-scope failures automatically enter the bounded repair path under the exact candidate delivery authorization. Scope discovery, exhausted budget, missing authority or ambiguous ownership pause work. A durable **Intervention** contains reason, candidate/evidence/finding IDs, consumed budget, proposed scope change and the bound planning intent/session. The existing conversation lets the human clarify, edit/compare/release a new spec, or abandon. Same-release budget extensions are deferred; chat alone cannot release a brief or change a grant. A new scope requires a new exact release and supersedes the old authority; do not auto-replace an existing delivered PR across releases. Budget decisions retain consumed history and invalidate stale pending actions. Cancellation/revocation fences new checks, repairs and delivery, and reconciles any in-flight effects.

## Durable draft delivery

**DeliveryIntent** binds execution/release/candidate/certification, repo identity, base ref/SHA, dedicated head ref, expected remote head, bounded publication grant and managed PR body hash. Use one durable delivery identity per execution and revision-specific effects. Steps are persisted before effects and independently recoverable: claim → recheck authority/evidence → materialize certified tree → commit and persist commit effect → publish branch → reconcile branch receipt → create draft PR once → reconcile PR receipt → attach watch.

The trusted delivery service owns Git/GitHub credentials; neither Codex nor verifier/reviewer receives them. Each revision has a managed checkout separate from its retained coding workspace. After checks settle and exact-tree/cleanliness checks pass, use that revision checkout to make a normal hook-respecting commit with the configured author. A repair receives a new revision checkout and local branch; keep the prior checkout and one durable remote PR branch. Missing author configuration blocks delivery; never invent author identity or bypass hooks. Prove the resulting commit tree equals certified `treeSha` and detect hook-generated working changes. Hook edits reject delivery and require fresh candidate evidence/checks/review; do not silently adopt them. Persist the commit SHA effect, parent/head-to-tree mapping and certification reference before push. Recover an already-created commit after a crash rather than creating another blindly. The original retained checkout and receipt remain unchanged. The UI and PR evidence distinguish checks on the certified tree from the later commit proven to contain that tree; commit-sensitive checks need their own actual-commit evidence before any such claim. Push only the registered remote and dedicated factory branch. Require the expected remote identity and fast-forward update; divergence or another writer's change needs intervention, not force-push. Record actual remote SHA before PR creation. Bind the PR with repo + head/base refs + an opaque stable factory marker, verifying provider identity and stored PR ID; a marker alone is not authority. Check existing open and closed PRs before creation. A closed/merged PR is not automatically replaced or reopened.

Persist intent before sending create and store returned PR ID/number/URL/head/draft receipt before reporting delivery. On timeout or crash after a write, reconcile through GitHub reads before retrying. Serialize writers using durable effect ownership; a lease expiry cannot by itself prove a timed-out write failed. If an uncertain create cannot be conclusively matched, stay `needs-reconcile`; do not issue another create merely because a read found nothing. Multiple matches or foreign branch/PR edits also require reconciliation. No exactly-once guarantee is inferred from an HTTP POST or model settlement.

Invalidate affected existing caches after mutations and use revalidated GitHub facts for delivery fences. Remote reads/writes are not transactional: record any authority/head change during an in-flight effect, reconcile its actual outcome and stop later actions. Never claim the effect was undone. Preserve human PR-body edits by leaving the initial body immutable. Label its tree/commit/checks as initial publication evidence; later repaired heads have current evidence in Neon. Managed body updates are deferred until conflict-safe provider write preconditions are established. Marker/identity drift blocks factory mutation. Keep the PR draft; do not automatically mark ready, approve, merge, deploy or post unrelated messages. Watch-attachment failure retries attachment to the stored PR, never PR creation.

## Watch ownership, outcomes and cleanup

Add **WatchOwner** as a durable discriminator (`legacy` or `factory` with execution/release/generation). Migrate existing watches to legacy behavior. Claim repo/PR ownership atomically before accepting repair feedback; reject takeover of an active legacy owner rather than cancelling it implicitly. Guard scheduler dispatch, already-queued events, configure/retry/message actions, prepared-diff mutation and cleanup at execution time. A factory PR may have shared read-only facts/notifications but exactly one mutation owner.

Persist normalized feedback with repo/PR/head/base identity, semantic fingerprint and generation in a durable inbox before advancing the existing watch watermark. Partial/rate-limited reads remain unknown and cannot consume missing feedback. Identical polling/webhook events create one repair intent; feedback arriving during repair is retained/coalesced for the next bounded admission. Stale-head feedback cannot authorize changes to a newer head. CI failure or human revision requests go through the same factory repair/certification/delivery path, never the old Autopilot editor. External branch movement invalidates certification and stops automatic writes.

The existing review surface shows candidate/spec/check/review provenance, exact delivery authorization and its target/permissions, draft PR and watch links, consumed/reserved/remaining repair and time budgets, intervention conversation, cancellation and retained-work warnings. Human merge remains explicit and separate from publication. Observe merged/closed facts through the watch, reconcile in-flight writers/delivery, and record an idempotent **Outcome** with PR identity, final head, merge SHA if supplied, observed time and result. Closed is not merged; unknown checks are not green; merge is not deployment success. Reuse existing merge/ref watch reporting where applicable without claiming release success.

**CleanupDecision** binds outcome, exact worktree/branch identity and ownership generation, dead-process proof and retained evidence policy. Stop/fence future repair intake before cleanup; verify no pending/uncertain effect or writer, no unexpected dirty/untracked content, and that all intended work is represented by the recorded delivered revision. Preserve non-ancestor squash/rebase outcomes using provider merge evidence rather than assuming ordinary merge ancestry. Retain ambiguous, failed, cancelled or unpublished work. Explicit discard is required to lose valuable local changes. Only the latest published revision checkout is automatically eligible after a 24-hour grace following an observed merge/close and exact receipt/root/head/cleanliness/death checks. Retain earlier revision checkouts, coding/repair workspaces, frozen-tree refs and evidence indefinitely. Seven-day attention and 30-day evidence pruning are deferred to an explicit retention/discard workflow; preserve durable receipts/audit identities. Default to local cleanup only; remote branch deletion is a separate explicit action. Repeated cleanup and outcome ingestion must be harmless.

## Acceptance and handoff policy

Deterministic acceptance must demonstrate bad evidence/stale certification rejection, ordinary bounded repair without another human gate, scope-change conversation and exhaustion intervention, duplicate-safe timeout recovery, exclusive factory ownership, human merge observation and safe cleanup. Use isolated repositories/runtime homes, mockdex and synthetic model/GitHub fixtures for controller tests. Those tests do not establish provider compatibility or live GitHub behavior.

A separately authorized postmerge live exercise must record actual CLI/model/auth compatibility, independent evidence, a bounded repair, one draft PR with recovery observation, watched feedback, human outcome and retained/cleaned work. Record date and tested source revision, limits, sanitized receipts and operator/manager decision. Unexercised cases stay pending; no premerge live gate is introduced. Keep credentials, private deployment identifiers/addresses, raw sessions and private evidence out of tracked docs, screenshots and PR bodies.

The manager additionally requires a final architectural review after all stack PRs exist, separate from the two independent static prepublication reviews and manager candidate review. The handoff tracks both stages separately. Work proceeds in the shared checkout with disjoint agent ownership; the manager owns plan integration, deviations and stack publication.
