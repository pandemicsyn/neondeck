Proposed architecture · for iteration

A small factory.
Neon runs the line.

Turn incoming work into scoped, verified pull requests. Neon owns intake, coordination, evidence, and follow-through. Codex or OpenCode owns the coding session.

Start with a persistent exe.dev host, SQLite, a deterministic state machine, and managed Git worktrees. Keep the agent harness and the machine it runs on independently replaceable.

Recommended first version: GitHub issue webhooks + manual intake; a lightweight model triages eligible work; Neon investigates and iterates on a plan with the human in a persistent planning conversation; the human releases the agreed brief into the queue; a configured Codex or OpenCode worker implements it; Neon verifies, opens a draft PR, and follows CI and review. A human decides whether to merge.

Linear fits the same intake contract as the next connector. Remote worker VMs fit the same execution contract as the next host adapter. Neither requires another factory or a new coding agent.

This is a design proposal, not shipped behavior. Existing capabilities below were checked against this checkout, including Flue 2.0.3. Proposed defaults are starting points for discussion.

The line, and who owns each station

Use a fixed sequence with explicit return paths. These are application phases; they do not require six long-lived agents or a workflow designer.

  1. Intakeevents → work
  2. Shapeintent → contract
  3. Buildexternal harness
  4. Verifyevidence + review
  5. Deliverdraft PR → merge
  6. Observefeedback → intake
1

Intake & triage

Services + lightweight triage model

Validate the event, refresh source facts, group related signals, and resolve the registered repository. Classify: implement, investigate, clarify, duplicate, defer, or decline. Ambiguous ownership stays in the inbox.

Output: a WorkItem, source links, reason, priority, and next action. Workspace allocation happens after queue admission.

2

Plan with the human

Neon planning model + human conversation

Neon investigates the repository, proposes a brief and approach, explains tradeoffs, and asks focused questions. The human and planner iterate in a persistent conversation while Neon updates the versioned brief, acceptance checks, and implementation plan. Use mocks or diagrams where they help make a decision. The human releases the agreed plan when the scope is clear.

Output: linked planning conversation + versioned TaskSpec + validation contract + approval to queue. Approval binds that spec version, repository, and authority.

3

Implement

Codex or OpenCode

The dispatcher leases a workspace and starts an external coding session with the approved brief. The harness explores, edits, runs tests, and manages its own tools and context. Neon monitors its process and results; it does not implement a second edit–tool–model loop.

Output: candidate revision, diff, session reference, check logs, and decisions or unresolved assumptions.

4

Verify & review

Checks + fresh reviewer

Run the configured checks independently, then review the exact candidate revision against the approved contract. Use Neon's read-only reviewer and behavior evidence where applicable. The reviewer reports findings and cannot fix them. Failures return a bounded fix brief to the coding adapter.

Output: revision-bound evidence and findings. Start with at most two repair attempts; then block for an operator decision.

5

Deliver & shepherd

Typed GitHub services + human

Publish the candidate branch and create or update one draft PR under the task's granted authority. Attach the plan, evidence, and risks. Existing PR watches collect CI and review feedback; any code repair returns through the same factory run. The human makes the merge decision.

Output: PR URL, delivery receipt, watch link, and merge/closed outcome.

6

Observe & learn

Existing watches + learning services

Follow available release/deployment checks. Record whether the task merged, was abandoned, or caused follow-up work. Feed actionable new signals into intake and settled outcomes into audited learning.

Output: outcome record and linked follow-up items. A merged PR is not proof of a successful deployment.

The practical synthesis: borrow upstream design and small slices from Dex, independent verification from Factory/StrongDM, and product feedback from PostHog. Keep human code review available in Neondeck's existing workbench. A green test suite alone cannot certify maintainability. Research notes ↗

Where humans plug in

Humans collaborate with the planning model, release the agreed scope, and decide whether to merge. Neon carries the work between those points. Additional interruptions happen when a concrete decision falls outside the authority already granted.

Each interruption arrives as a concrete decision

In the Factory view's Needs attention queue, show who needs to act, why work is waiting, Neon's recommendation, the brief/diff/evidence being decided on, and available actions. Link directly to the planning conversation or PR workbench so the human can ask questions and iterate before deciding. Record the decision, actor, time, scope, and bound spec/candidate version using the existing approval and audit patterns.

Required decisions leave the run in waiting-human until answered; silence or a timeout never grants approval. New evidence that changes the decision invalidates the old request. Notify once when attention is needed and again only for a meaningful change or a configured reminder. Waiting releases coding compute after a safe checkpoint while preserving the conversation and work artifacts.

Between human touchpoints: Neon handles admission, classification, worker creation, monitoring, checks, bounded repairs, authorized publication, and PR watching. Humans can inspect, steer, or cancel at any time without becoming the message courier between components. Skipping plan release for selected small tasks is a later explicit policy option; v1 keeps plan release and the merge decision human-owned.

Separate delivery, source item, and work item. Ten updates to an issue are ten deliveries, usually one source item, and not ten coding jobs. Several source items can describe the same work.

The inbound sequence

  1. Receive and persist. Verify the provider signature over raw bytes before trusting payloads. Enforce body limits, expected event/action types, and configured source ownership. Commit the delivery and enqueue its processing in one SQLite transaction; acknowledge immediately afterward.
  2. Deduplicate and refresh. Unique key: provider + connection + delivery ID. Track source ID and semantic fingerprint separately. Re-fetch current state so delayed or reordered deliveries cannot overwrite newer intent. Repeated fingerprints do not wake Neon.
  3. Route deterministically. Check source eligibility, repo mapping, linked active runs, terminal state, and configured policy before model work. Cross-provider duplicate suggestions need a confirmed link; similar titles alone cannot merge tasks.
  4. Classify eligible work. Run a bounded triage job with a configurable inexpensive model, source facts, and bounded repo/product context. Persist a typed triage decision, confidence, rationale, and missing information. External issue bodies are task data and cannot grant permissions.
  5. Open collaborative planning. Route actionable work to a separate Neon planning conversation. The planning model investigates, proposes, and revises the brief with the human before queue admission. Uncertain classifications can request deeper investigation. Posting a question back to a tracker requires configured outbound authority; clarification in Neon uses the planning conversation.

GitHub recommends fast acknowledgement and delivery-ID deduplication. Linear documents HMAC validation and timestamp checks; apply its freshness check and deduplicate delivery IDs. Plan explicit reconciliation for missed GitHub deliveries rather than assuming automatic retries. GitHub webhook guidance · Linear webhooks

Changes arriving while work is already running

Comments and edits append source revisions; they do not silently rewrite the running spec. Material scope changes pause at a checkpoint and require a new approved spec version. Source closure requests cancellation, which stops the worker before releasing its lease. Reopening a terminal item requires a new explicit run. Ignore the factory's own status writes as triggers. Unknown repo, unavailable credentials, provider rate limits, and invalid model output remain visible inbox states with retry times or operator actions.

Keep a scheduled reconciliation pass for opted-in source items and delivery failures. Use bounded retries with backoff for transient reads; permanent mapping/authentication errors should not spend model tokens.

Keep GitHub issues useful to collaborators

Recommended: enable concise issue updates as an explicit repository onboarding choice. People following the issue should know whether Neon picked it up, what scope was agreed, what needs attention, and where the PR is. Neondeck keeps the authoritative run state, planning conversation, versioned artifacts, and audit history; GitHub keeps the original request and contributor discussion.

One maintained status comment

After eligible work is accepted for planning, create one Neon-owned status comment per linked work item. Update it on meaningful transitions: shaping, queued, implementing, blocked, PR ready, merged, failed, or cancelled. Include the current run, last update, concise blocker/next action, agreed scope and acceptance summary with spec version, and PR link when available. Render only committed facts; mark proposed scope as draft until released.

Questions and replies

Default to status writeback after onboarding consent, with off available. Posting an actionable question is a separate “Ask on GitHub” action: Neon drafts it, the human can edit and send it. A later status-and-questions policy can authorize this automatically. Questions become distinct comments so collaborators have a clear place to reply; routine progress edits should not be relied on as an attention-delivery mechanism.

Subscribe to issue-comment changes for linked items. Bring replies into the existing planning conversation as attributed source updates. Re-check identity and relevance; comment text cannot release a plan, change execution authority, or overwrite the accepted spec. Neon proposes any resulting brief revision in the planning UI. Issue closure requests cancellation as already defined; an implementation run finishing must not close an issue prematurely. Use a plain PR reference initially; add closing keywords only when the approved delivery scope actually resolves the issue.

Use the existing delivery and audit mechanisms

Add typed issue create/update-comment operations over the existing GitHub client. The current PR-comment helper already uses the shared Issues API; generalize its naming and add the update operation. Persist the comment ID, owned marker, desired content hash, source revision, and delivery receipt. Serialize writes per work item, coalesce superseded updates, and reconcile uncertain creates before retrying. Verify ownership before editing and suppress only our own correlated status events to avoid triggering another run.

Failed writeback shows “GitHub update pending” with retry status in Neon. Coding can continue within its existing authority while that update retries; a question awaiting an answer still blocks dependent work. A human-edited or deleted status comment requires reconciliation rather than blindly recreating or overwriting it. GitHub comment edits never become the factory's database.

Humans plan with Neon

The lightweight classifier routes work. A separately configured planning model does the investigation, drafting, and revision work with the human. Use Neondeck's durable Flue conversations and existing chat UI, linked to the work item before any coding run exists.

  1. Neon proposes. Read relevant code and product context, identify unknowns, and present a brief with the intended outcome, acceptance criteria, constraints, and a suggested approach. For substantial work, show interfaces, likely file changes, and vertical slices. For UI decisions, share a mock; for architecture, share a diagram or concrete alternatives.
  2. The human and model iterate. The human asks questions, corrects assumptions, or chooses an approach. Neon investigates further and updates the brief and plan through typed services. Show what changed between versions and which decisions remain open. Scale the conversation to the task: a tiny fix can settle quickly; larger changes need more design discussion.
  3. The human releases a specific version. Present the current brief, validation contract, remaining assumptions, and proposed authority together. Queue that agreed version. Merely discussing or editing a plan does not start a coding agent.
  4. Neon hands off the agreed context. Package the spec, relevant research, resolved decisions, selected guidance, and validation contract for Codex/OpenCode. Keep the full planning history available by reference; avoid dumping the whole chat into the coding prompt.
  5. Consequential discoveries return to this conversation. If implementation finds a faulty assumption or needs a material scope change, checkpoint the worker and bring the finding, evidence, and proposed revision back to the human and planner. Resume after agreement on the new spec version. Ordinary in-scope repairs stay within the already granted authority.

The planning view shows the conversation alongside the current brief, plan, open questions, and version history. Persist its conversation ID, model/context version, and decision records on the work item so it survives restarts and can be reopened from the run or PR. Each model turn is bounded; the conversation persists while waiting without holding a coding process or worker VM.

The human touchpoints map distinguishes collaboration, required gates, and conditional interventions. After plan release, Neon coordinates implementation, verification, and draft-PR delivery within that authority without requiring the human to relay messages between phases.

External coding sessions, owned from start to cleanup

A factory run is the durable job. A coding session is one replaceable participant. Do not use a provider session ID as the run ID, and do not treat a worktree, a VM, and a conversation as the same resource.

CodingAgent adapter

Owns provider-specific start/resume arguments, event parsing, session identity, final result extraction, and transcript export. Initial adapters: Codex CLI and OpenCode CLI.

ExecutionHost adapter

Owns workspace preparation, process supervision, logs, cancellation, artifact collection, and cleanup. Initial adapter: local process on the Neon host. Future: existing remote host or disposable exe.dev VM.

Session lifecycle

  1. Reserve. Persist run/attempt IDs and acquire the task/workspace lease before allocating resources. Start with one coding attempt globally and one writer per repository; queued work waits without an agent process.
  2. Prepare. Resolve and record the base SHA, create an app-owned worktree and agent/factory/<work-item-id> branch, install dependencies using trusted repo setup instructions, and assign per-run scratch directories and dev-server ports. Never code in the user's primary checkout.
  3. Freeze context. Materialize the approved brief, acceptance contract, relevant source snapshots, repo instructions, selected skills, and memory snapshot. Record their versions/hashes plus harness version/model. Native harness compaction remains the harness's job. A new spec or deliberate context refresh creates an explicit boundary.
  4. Launch and track. Run under a supervised job with a unique attempt token, cwd, start time, PID/process-group or service identity, log files, and eventual provider session ID. A small runner wrapper records heartbeat and atomic exit receipts. It launches the existing CLI; it has no model/tool loop.
  5. Finish and collect. Stop the writer, capture dirty/untracked changes and the candidate commit, logs, decisions, and test artifacts. The factory records the candidate SHA before independent verification. An exit code of zero means the process finished, not that the task is done.
  6. Repair or release. Resume a known session for a narrow fix, or use a fresh session with a handoff summary when context or host changed. Every retry gets a new attempt record and its own budget. Same task/branch does not mean simultaneous workers.
  7. Clean up. Stop the CLI and all owned child services; collect evidence; revoke temporary credentials; release ports; confirm no live writer; then release the lease. Remove the worktree only when existing cleanup policy permits and all local commits/dirty work are preserved or explicitly discarded.

Isolation in v1 is operational. Separate worktrees, private agent homes/state, allowlisted environment, and owned processes prevent accidental session collisions. They do not create a security sandbox: worktrees share Git metadata, and same-user processes may access each other's files. Limit this mode to trusted repositories and tasks. Full OS isolation is a later host capability.

Give workers only their selected model authentication and required test credentials. Keep webhook secrets, deployment credentials, and GitHub write authority in the control service. Harness-specific config/state roots must be isolated and tested; do not inherit the operator's global plugins, MCP servers, or login environment wholesale. Keep native harness permission controls where supported. Neondeck's shell policy does not automatically govern a separate CLI's internal tools.

Restart, cancellation, and a worker we cannot locate

The supervisor writes logs and terminal receipts to disk independently of Neon's in-memory process map. At startup, reconcile each active attempt using its host, service identity, start token, receipt, and workspace. If still running, resume monitoring; do not launch another worker. If ended, import its evidence. If ownership or outcome is uncertain, mark needs-reconcile and quarantine the workspace.

A lease timeout does not prove an external CLI stopped writing. Fence future publication, stop or prove the old process dead, and only then issue a replacement lease. Cancellation sends TERM to the owned process group/service, follows with KILL after a bounded grace period, and confirms termination. A disconnected SSH channel is not cancellation. Persist cancellation intent so a restarted controller finishes it.

Retention and cleanup policy

Proposed defaults: stop compute when a task waits for human input; retain the worktree while its PR is active; retain a clean, fully published successful workspace for 24 hours after terminal outcome. Failed, dirty, adopted, or unpublished work stays retained under existing policy. After seven days, surface a cleanup decision rather than deleting valuable work automatically. Keep redacted logs and session exports for 30 days, and durable outcome/provenance records independently of compute.

Future per-run VMs follow the same rule: collect and verify artifact transfer before deletion. Record explicit resource ownership so cleanup cannot remove the persistent Neon VM, a user-provided VM, or an adopted checkout. Cleanup is idempotent and retryable; failed cleanup stays visible. Provider-managed history may have its own retention policy.

exe.dev hosts Neon now, workers later

Run one Neon control process under a service manager on a persistent Linux VM. Keep NEONDECK_HOME, app SQLite, Flue SQLite, artifacts, and registered repositories on persistent disk. Back up both databases consistently with their SQLite journaling mode; do not clone the live control VM as a worker template.

Public webhooks without making the deck public

exe.dev terminates TLS and supports one public proxy port while alternate ports in the 3000–9999 range remain private. Set the primary public port to a dedicated minimal Hono webhook app, for example port 8080, exposing only POST /hooks/github, POST /hooks/linear, and a minimal health response. The future remote handoff

The host adapter provisions or selects a machine, checks out the pinned base SHA, transfers the brief and any unpublished candidate via a Git bundle/patch, then runs the same supervisor and coding CLI there. Return a verified Git bundle or pushed candidate ref plus artifact manifest. Never assume a local absolute path is meaningful on the remote host.

Persist VM name, SSH destination, ownership, environment fingerprint, and retention state. Reconcile a timed-out VM-create operation by its recorded unique name before retrying. Use returned connection metadata; exe.dev's SSH API may return a destination with a required username. Poll a remote receipt/log cursor instead of keeping a model turn or SSH stream alive.

For previews, allocate and register a private URL, readiness probe, port, expiry, and service stop handle. Collection and publication are explicit actions. exe.dev VMs are persistent: stopping a coding process is not deleting its machine or ending all resource usage. Support clean images, setup scripts, and deletion through the provider adapter when this slice ships. SSH API · Create VM · Delete VM

What to remove, and when

Remove duplicated coding orchestration from the factory path as soon as external adapters work. Later, retire the writable Flue PR-owner feature only after existing watches can migrate and equivalent repair behavior is verified. Replace Kilo-only labels on shared job UI with “Coding runs”; retain provider-specific inspection where useful. Consolidate duplicate job schedulers rather than introducing a factory cron engine.

Keep Neon chat, reviews, watches, schedules, and learning. They become factory components and remain useful independently. Correct stale Flue “workflow/action” terminology in touched product docs; this checkout uses Flue 2 agents/tools and app-owned orchestration, not the old framework workflows.

Work state that survives restarts

Use one coordinator loop that advances runnable records from persisted evidence. Flue handles bounded triage, planning, and review submissions. The coordinator handles queueing, dependencies, retries, leases, external coding processes, and delivery.

Transitions compare the current version and lease generation. Admission plus the pending effect is transactional. Reconcile external effects after restart; do not promise exactly-once remote execution. A deterministic run key and durable effect intent prevent ordinary duplicate starts, while uncertain outcomes remain explicit.

One backend surface

Proposed operations: submit, triage, open/message planning conversation, revise brief/plan, release spec version, queue, pause, cancel, retry, approve delivery, reconcile, and cleanup. Use schema-validated domain services with request idempotency keys. Expose /api/factory/…, CLI commands, and model-facing tools over those same services.

One operator view

Add a Factory view: Inbox, Active, Needs attention, and History. Each work item opens a planning conversation alongside its versioned brief, plan, and open decisions. Each run links back to that conversation and opens its timeline, external session, diff/evidence, and PR. Needs attention surfaces the assigned human decision, recommendation, bound version, and next actions from the touchpoints map. Neon can explain “why blocked?” from those records. Use the existing event stream to refresh clients; durable state remains authoritative.

Keep a small validated factory profile in runtime config: eligible sources/repos, triage model, planning model, coding agent provider/model, execution host, setup/check commands, publication authority, concurrency, retry/time limits, and retention. Changes go through typed config tools. Avoid a generic graph DSL or arbitrary executable webhook configuration in v1.

Flue 2.0.3's bundled guide/durability documents durable submission settlement and at-least-once side effects. It does not make an external CLI or VM durable automatically. Public durability guide (live docs may evolve).

Define “done” before starting the worker

The spec includes user-visible acceptance scenarios, required repository checks, excluded scope, and evidence requirements. Validate both behavior and the shape of the change: unexpected files, dependency additions, changed tests, and departures from the plan go into the reviewer packet.

The verifier runs configured commands against a frozen candidate in a separate verification workspace where needed, with separate test data. Record command, cwd, environment/toolchain fingerprint, exit code, logs, and candidate SHA. Require the working tree to remain unchanged or capture and review any generated changes. The agent cannot weaken the externally stored validation contract through its result report.

For UI work, require a small browser scenario and a screenshot or recording when the task calls for it; for backend work, use observable inputs/outputs and regression checks. A missing environment produces “blocked validation,” not a pass. Fresh agent review adds judgment, but it does not substitute for executed evidence or the human merge decision.

Delivery is its own side effect

  1. Confirm the current candidate, approved spec, successful validation, and publication authority still match. Base/head movement invalidates affected checks and review.
  2. Use the trusted delivery service to commit if needed, push only the intended branch, and create/update a draft PR. The default queue approval can grant this bounded publication. Merge, deploy, or unrelated tracker messages are separate authorities.
  3. Record an effect key and correlate the PR using repo + branch + run marker. On a network timeout, query GitHub for the branch/PR before repeating the action. Persist actual receipts before showing “published.”
  4. Attach the existing PR watch with factory ownership. Deduplicate CI/review feedback, acquire the same writer lease, and invoke the external coding adapter for repairs. Enforce a total run budget as well as per-repair limits.

Defaults that keep the naive factory bounded

Start with one active coding worker, a 45-minute implementation attempt, two repair attempts per candidate cycle, and a three-hour cumulative execution budget per run. Human waiting time is separate. These are configurable admission limits, not claims about normal task duration. Cap queued-ready work when review backlog grows. Record provider usage when available; an unavailable dollar estimate stays “unknown.”

Measure time to reviewable PR, first-pass validation, repair count, human review/rework time, outcome cost, cancellation/cleanup failures, and later reverts or linked regressions. Retain a small set of real completed tasks as an evaluation set before expanding autonomy. Learning changes future guidance through the existing audited system.

A worked example: one issue, two coding attempts

A maintainer labels a GitHub issue: “Watch notifications repeat after reconnect.” The delivery is persisted once; Neon fetches the current issue, links related watch behavior, and drafts a brief: reconnecting must not resend already-handled feedback, while genuinely new feedback still notifies.

The operator queues that brief. The coordinator resolves the base SHA and creates a managed worktree. Codex implements a candidate and reports passing checks. Independent verification finds that new feedback is now suppressed. The reviewer records that failure against the candidate; the coordinator issues a scoped repair brief to the same recorded Codex session.

The second candidate passes the acceptance cases and review. Neon publishes one draft PR and follows CI. A duplicate webhook adds no work. A controller restart reconstructs the run from records. The human reviews and merges; the release watch reports what it can observe, and the clean published worktree becomes eligible for cleanup. Learning receives one settled outcome, including the failed first attempt.

Included in the initial target

Slices 1–4: one repo per task, GitHub/manual intake, both coding harness choices, explicit gates, real draft PR delivery, repair through existing PR feedback, durable inspection, and safe cleanup on one exe.dev host.

Deferred deliberately

Linear can replace GitHub-first if preferred. Otherwise it follows as slice 5. VM-per-run execution is slice 6. Also defer multi-repo graphs, parallel branch synthesis, autoscaling pools, digital twins, auto-merge/deploy, custom model gateways, and self-modifying factory policies.

Decisions to revisit together

GitHub or Linear as the first source; default Codex versus OpenCode profile; whether queue approval includes draft-PR publication; how much existing PR-owner behavior to retire after migration; and whether same-host contention warrants pulling the remote slice forward. The proposal chooses workable defaults so none of these need block the first review.

What the reading changed

The sources disagree about whether unread code can be trusted. The useful common ground is narrower: deliberate intake, bounded tasks, explicit context, independent evidence, traceable decisions, and feedback. The architecture above is a synthesis for Neondeck, not a claim that these vendors use identical designs or that their reported results will transfer here.
